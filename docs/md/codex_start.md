
- 위와 같이 이 문서를 읽고 진행하라는 사용자 요청을 받으면 아래 범위의 실제 HTML 제작을 시작함.

## 4. 착수 승인과 질문 기준

- 사용자의 “이 문서를 읽고 진행해줘” 요청을 위 HTML 제작 범위의 착수 승인으로 취급함.
- 구현 전에 이해한 내용·방향·수정 파일·브랜치 여부·주의사항을 짧게 설명한 뒤 작업을 계속함.
- 같은 범위에 대해 “이대로 진행할까요?”라는 질문으로 다시 멈추지 않음.
- 계획서의 “HTML 제작은 후속 작업” 문구는 계획서를 작성했을 당시의 단계 설명임. 이 시작 요청이 그 후속 제작의 실행 지시임.
- 색상·간격·표현 방식 등 되돌리기 쉬운 세부 선택은 아래 기본안과 계획서 안에서 결정함.
- 파일 삭제·이동, 새 라이브러리나 빌드 도구 추가, 기술 스택 변경, 배포, Git 초기화는 위 범위에 포함되지 않음.
- 범위 밖 변경이 꼭 필요하면 이유와 구체적인 대상을 설명하고 확인함.
- 도구의 실제 권한 승인이 필요하면 권한 절차를 따름. 문서의 작업 승인을 권한 우회로 사용하지 않음.

## 6. HTML 제작 기본안

### 구조와 실행

- HTML·CSS·JavaScript로 구현함. 새 프레임워크·패키지·빌드 과정은 추가하지 않음.
- 로컬에서 `presentation/index.html`을 직접 열 수 있게 함.
- CSS와 JavaScript는 상대 경로로 연결함.
- 기본 실행에 인터넷·외부 CDN·Google Fonts·원격 이미지·API 키·서버가 필요하지 않게 함.
- 콘텐츠를 `fetch()`로 읽거나 ES module import를 사용해 `file://` 실행을 막는 구조를 기본안으로 넣지 않음.
- 발표 데이터와 노트는 HTML 또는 일반 JavaScript 안에 둠.
- 1920×1080의 16:9 무대를 화면에 맞춰 비율 유지 확대·축소함.
- 화면이 작아져도 슬라이드를 웹 문서처럼 세로 재배치하거나 스크롤시키지 않음.

### 문구와 화면

- 한 장에 중심 메시지 하나를 둠.
- 본문은 가능하면 1~3줄로 제한함. 대본을 화면에 붙여 넣지 않음.
- `WHY?`, `FLYBY`, `ROSETTA` 전환 장면을 살림.
- 필요한 경우 같은 장 안에서 질문·현상·답을 단계 공개함.
- 숫자·벡터 패널, 슬라이더, 실행 버튼을 청중 화면에 추가하지 않음.
- 발표 흐름과 관계없는 장식용 카드·설정 창·기술 설명을 넣지 않음.

### 조작과 노트

- 오른쪽 방향키·Space로 다음 단계 또는 다음 장으로 이동함.
- 왼쪽 방향키로 이전 장으로 이동함.
- 슬라이드 전체가 일정 시간마다 자동으로 넘어가지 않게 함.
- 현재는 개별 애니메이션을 시작하지 않음. 그림과 수동 단계만 즉시 표시함.
- 장면을 떠나면 이전 장면의 타이머와 애니메이션을 정리함.
- 마지막 장은 종료 상태를 유지함. 첫 장으로 자동 복귀하지 않음.
- 슬라이드별 발표자 노트는 기본 청중 화면에서 숨김.
- 노트는 HTML의 비표시 요소나 구조화된 데이터로 보관할 수 있음. 새 발표자 도구 UI는 필수 아님.

### 과학적 표현

- 계획서의 과학적 표현 점검 기준을 적용함.
- 행성 기준의 통과 전후 속력과 태양 기준 속력 변화를 섞지 않음.
- 행성 표면에서 탐사선이 튕기는 모습으로 그리지 않음.
- 가속·감속·방향 전환을 설명과 일치하게 표현함.
- 로제타의 순서는 지구 출발 → 지구 → 화성 → 지구 → 지구 → 67P로 유지함.
- 목성 도착 이전의 시간이 목성에서 이후에 받는 중력 도움 때문에 줄었다고 설명하지 않음.
- 실제 데이터가 아닌 궤적은 개념도라고 구분함.
- v2의 약 22초 반복 시간과 v1의 속력 수치를 전체 발표의 필수조건으로 복사하지 않음.

## 8. 검사와 사용자 확인

### AI가 수행할 검사

- 모든 JavaScript의 문법과 명백한 참조 오류 확인.
- HTML·CSS·JavaScript 상대 경로와 파일 존재 여부 확인.
- 01~20장 순서·문구·노트·장면 정의의 대응 확인.
- 다음 단계·다음 장·이전 장 처리와 마지막 장 종료 로직 검토.
- 장면을 떠난 뒤 타이머나 그리기 루프가 계속 쌓이지 않는지 코드 점검.
- 오프라인 기본 실행에 필요한 파일이 모두 로컬에 있는지 확인.
- 모션 감소 설정에서 핵심 내용을 읽을 수 있는지 구현 검토.
- 기존 자동 검사가 이번 변경에 직접 관련될 때만 실행함. v1 물리 검사를 전체 발표나 v2의 검증으로 보고하지 않음.

### 사용자가 확인할 항목

- 실제 브라우저에서 파일 열기와 전체 화면 표시.
- 글자 크기·겹침·잘림·색 대비.
- 키보드 이동과 단계 공개.
- 애니메이션의 속도·반복·설명 타이밍.
- 발표 시간과 교실·프로젝터에서의 가독성.

- 브라우저 실행·UI 조작·시각 검수는 사용자가 수행함.
- AI가 실행하지 않은 항목을 `정상 작동`, `실제 테스트 통과`, `UI 문제 없음`으로 기록하지 않음.
- 코드 검사 완료와 사용자 화면 확인 대기를 구분함.
- 단순 문구를 그대로 따라 확인하는 형식적인 테스트 파일을 늘리지 않음.

## 9. Git과 문서 마무리

- Git 저장소가 없으면 초기화·remote 추가·커밋을 하지 않음.
- Git 저장소가 있으면 적용되는 프로젝트·전역 규칙을 따름.
- 새 작업 브랜치가 필요하면 현재 상태 확인 후 `feat/html-presentation`을 후보로 사용함. 같은 작업 브랜치가 있으면 이어서 사용함.
- 관련 없는 미커밋 변경은 보존함. 임의로 stash·reset·restore하지 않음.
- 사용자 확인이 필요한 경우 main 병합을 먼저 하지 않음.
- README에는 실제로 구현된 실행 경로·조작·상태만 반영함.
- 개인 작성용 `plan.md`, `design.md`, `progress.md`, `requirements.md`, `content.md`, `script.md`, `summary.md`는 자동으로 채우지 않음.
- 진행 기록은 아래 구역을 사용함. 문서마다 같은 대본이나 스토리보드를 복제하지 않음.
